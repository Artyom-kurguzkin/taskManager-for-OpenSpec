# Research: logging and traces

Sources (all 2024+ docs, current .NET 10):
- Microsoft Learn, "Logging guidance for library authors" and the logging overview (https://learn.microsoft.com/dotnet/core/extensions/logging-library-authors): without a host, build an `ILoggerFactory` with `LoggerFactory.Create`/providers and make one logger per class (category = type name); use message templates, never interpolation. Taken: one static factory, `AppLog.For<T>()`, templates.
- Microsoft Learn, "Distributed tracing concepts" and the instrumentation/collection walkthroughs (https://learn.microsoft.com/dotnet/core/diagnostics/distributed-tracing-concepts): an `ActivitySource` creates Activities only when an `ActivityListener` subscribes; the default id format is W3C since .NET 5, so a trace id is 32 hex chars. Taken: one `ActivitySource("RepoTasks")`, one process-wide listener that logs start and stop with the duration.
- Microsoft Learn, `ActivityTrackingOptions` (https://learn.microsoft.com/dotnet/api/microsoft.extensions.logging.activitytrackingoptions) and the Activity.Current correlation write-up (https://oneuptime.com/blog/post/2026-09-11-dotnet-activity-current-correlation-logging-scopes/view): the logging stack correlates by reading `Activity.Current` (TraceId) at log time, and a child activity changes `Current`, so read it per line and do not cache a span id. Taken: the line formatter reads `Activity.Current?.TraceId` per entry; Task.Run flows the ExecutionContext, so a queued write and the scan it starts are children of the command with no manual hand-over.
- Per-run files for desktop apps: the search found no 2024+ Microsoft source on keeping the last N session logs (rolling-file providers such as NetEscapades keep a retained-file-count). Taken: own small file provider, one file per process, newest 20 `run-*.log` kept, the rest deleted at startup.
No new package: the shared ASP.NET Core framework already carries Microsoft.Extensions.Logging; the console sink is a plain writer sharing the file's line format.
