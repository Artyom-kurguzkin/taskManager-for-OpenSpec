# The app answers at once

Measured on a copy of this board (53 items) in the real app on the hidden desktop, before and after:

| | before | after |
|---|---|---|
| tick a subtask, visible | 600-800 ms | 78 ms |
| open an item from the board | 700-980 ms, 2 redraws | 284 ms, 1 redraw |
| switch to Worklog | ~1 s, 5 redraws | 123 ms, 1 redraw |
| a write plus the re-read behind it | 290 + 230 ms | 10 + 17 ms |
| a git question | 75-110 ms each | 0 ms after the first per commit |

What changed: work items and notes are cached per change folder (a folder is re-read only when its files' names, sizes or times changed, or the app itself wrote there); a write no longer re-reads the board first; the duplicate-id scan runs only when a folder appears or goes; git history is read once per HEAD (one git log, bounded to 5000 commits) and answered from memory; pages load once per navigation and once per change, with nothing expensive during drawing, and several change events within 50 ms become one redraw (skipped when nothing was written since the last one). The board's list no longer renders flat and regroups, and the split-screen list is not built when the window is too narrow to show it. `tests/perf-probe.ps1` measures these steps in the real app.

Known: an outside edit that keeps a file's size and lands in the same filesystem time tick as the last read is not noticed until the next change. Going back to the board still shows a second, later DOM change from the scroll-hint script, not a redraw.
